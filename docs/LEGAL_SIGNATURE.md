# 전자서명 법적 검토 및 v2 강화 방안

> ⚠️ **면책**: 이 문서는 법률 자문이 아니라 개발/기획 판단을 위한 내부 정리다. 실제 서비스 출시·마케팅 문구 확정 전에는 전자서명·전자거래 전문 변호사의 검토를 받아야 한다. 아래는 한국법 기준 쟁점 정리다.

## 0. 한 줄 요약

FreeSign v1 간이 서명은 **계약을 무효로 만드는 문제는 없지만**, 분쟁 시 "이 서명이 진짜다"를 서비스가 입증하기 어렵다는 **입증력(증거력) 리스크**가 핵심이다. 코드가 `legalEffect: "none"`으로 명시하고 면책 문구를 노출하는 현재 설계는 이 리스크를 인지하고 격리한 타당한 형태다. v2에서 신원확인·제3자 타임스탬프·완결증명서를 더하면 "법적 효력 있는 서명"에 근접한다.

---

## 1. v1 전자서명이 실제로 쓰이는 곳

계약이 성사(`signed`)되는 경로는 **두 가지**다. 인보이스/결제에는 서명 개념이 없다.
- **(A) 캔버스 서명** — 사용자가 직접 만든 계약을 캔버스로 서명해 성사시키는 주 경로(아래 흐름).
- **(B) 계약 불러오기** — 발주처가 보낸 원본 PDF를 업로드하면 **캔버스 서명 없이** 곧바로 성사 저장한다(`createImportedContract` → `import_signed_contract_with_event` RPC, 이벤트 `contract.imported`). 이때 `doc_hash`는 조항 JSON이 아니라 **업로드한 원본 PDF 바이트**로 산출하고(`computeFileHash`), 상세 화면은 불러온 계약(`source_pdf_url != null`)에 서명 카드를 숨긴 채 "원본이 증빙"으로 처리한다. 따라서 "서명은 한 군데뿐"이 아니라, **원본 PDF 증빙 경로가 별도로 존재**한다.

**(A) 캔버스 서명 흐름**
1. 계약 상세 페이지에서 `status === "draft"`일 때만 캔버스 서명 패드 노출 (`src/app/(dashboard)/contracts/[id]/page.tsx`, `status === "draft"` 분기)
2. 캔버스 서명 PNG를 `POST /api/contracts/[id]/sign`으로 전송 (`src/components/signature-pad.tsx`)
3. 서버 라우트(`src/app/api/contracts/[id]/sign/route.ts`):
   - private 버킷에 서명 이미지 업로드 (`{user_id}/{contract_id}/signature.png`, DB엔 key만)
   - 계약 조항을 canonical JSON 정렬 후 **SHA-256 해시**(`doc_hash`) 산출 (`src/services/signature/provider.ts`의 `computeDocHash`)
   - 서버에서 `signature_meta = { signer(이메일), signed_at, ip, ua }` 구성 — **클라이언트 입력 금지, 전부 서버에서 채움**
   - **`sign_contract_with_event` RPC**로 `status: draft → signed` UPDATE + `doc_hash`/`signature_meta` 기록 + `contract_events` INSERT를 **단일 트랜잭션**으로 원자적 처리(개별 UPDATE/INSERT 순차 아님)
4. 되돌리기(`signed → draft`)는 `transitionContractStatus`가 `transition_contract_status_with_event` RPC에 `p_reset_signature_artifacts` 플래그를 넘겨 서버에서 서명 이미지·해시·메타를 초기화한다 (`src/app/(dashboard)/contracts/actions.ts`)

**핵심**: 코드가 명시적으로 `legalEffect: "none"`을 반환하고, UI/PDF에 "v1 간이 서명은 법적 효력이 없는 기록용" 면책 문구를 단다. 실제 법적효력 서명 API는 `SignatureProvider` 인터페이스 뒤 교체 지점으로 v2에 미뤄져 있다 (`docs/ADR.md:18`, `docs/PRD.md:21`).

## 2. 법적 쟁점

### 2-1. "전자서명이라서 무효"는 아니다

2020년 **전자서명법 전부개정(시행 2020.12.10)**으로 공인인증서(공인전자서명)의 우월적 지위가 폐지됐다.

- **전자서명법 제3조**: 전자서명은 "전자적 형태라는 이유만으로" 서명으로서의 효력이 부인되지 않는다. 당사자가 합의해 쓰기로 한 전자서명은 서명·기명날인으로서 효력을 가진다.
- **전자문서 및 전자거래 기본법 제4조**: 전자문서도 전자적 형태라는 이유만으로 효력이 부인되지 않는다.
- 한국 계약법은 **낙성계약 원칙** — 원칙적으로 서면·서명 없이 합의만으로 계약이 성립한다.

→ 캔버스 서명이라 해도 계약이 무효인 것은 아니다. 코드의 `legalEffect: "none"`은 법적으로 정확히는 **"효력이 없다"가 아니라 "효력을 보장/증명하기 어렵다(입증력이 약하다)"**가 맞다.

### 2-2. 진짜 문제는 "입증력(증거력)"

분쟁 시 법원이 보는 세 요건에서 v1은 모두 약하다.

| 요건 | 의미 | v1의 상태 | 리스크 |
|---|---|---|---|
| **본인확인(신원)** | 누가 서명했나 | 이메일 로그인 신원뿐. 캔버스 그림은 필적감정 대상도 아님. 휴대폰·신분증 인증 없음 | 높음 — "내가 안 했다" 부인에 취약 |
| **무결성(위변조)** | 서명 후 문서가 안 바뀌었나 | `doc_hash`(SHA-256)로 원리 재현 | 중간 — 아래 참조 |
| **부인방지** | 나중에 발뺌 못 하게 | 감사 로그(ip/ua/시각) 있으나 자체 기록 | 높음 |

**무결성 해시의 결정적 한계**: 해시를 **서비스 운영자가 자기 DB에 저장**한다. 제3자 **신뢰 타임스탬프(TSA)나 신뢰기관 앵커링이 없어** "운영자가 나중에 해시를 바꿔치기하지 않았다"를 증명할 수 없다. 자기가 자기 증거를 만드는 구조라 상대가 다투면 신뢰성이 크게 약해진다.

### 2-3. "인정전자서명" 이점을 못 받는다

개정 전자서명법의 **전자서명인증사업자 평가·인정 제도**에서 인정받은 서명(공동인증서, 카카오·네이버·PASS, 토스 등)은 신원확인·무결성에서 사실상 추정력에 가까운 이점을 받는다. v1 자체서명은 이 범주 밖이라 **분쟁 시 서명의 진정성립을 우리가 전부 입증해야** 한다.

### 2-4. 계약 유형별 법정 방식 요건

프리랜서 **용역/도급 계약**은 대부분 방식 자유라 간이 서명으로도 성립에 큰 문제가 없다. 다만 일부는 법이 서면·특정 방식·교부의무를 요구한다.

- **근로계약**에 가까운 형태(위장도급 논란 소지): 근로기준법상 서면 명시·교부 의무
- **방문판매·전자상거래·할부거래**: 청약철회·서면 요건
- **하도급거래**: 하도급법상 서면 발급 의무

→ FreeSign은 사용자가 어떤 계약이든 담을 수 있으므로, **"모든 계약에 법적 효력을 보장한다"는 뉘앙스는 절대 주면 안 된다.**

### 2-5. "돈이 오갈 때" — 서명과 별개 리스크

**현재 코드는 실제 자금 이체를 하지 않는다.** 인보이스는 결제 *상태*를 토글할 뿐이고(`src/services/payment/provider.ts`), 돈은 당사자끼리 계좌이체로 직접 오간다.

- 지금 구조에선 **전자금융거래법** 직접 규제(전자금융업 등록 등) 대상이 원칙적으로 아니다.
- 단, 앞으로 **에스크로/대금 정산/PG 연동**으로 우리가 자금 흐름에 개입하면 → 전자금융업 등록, 자금세탁방지, 정산 책임 문제가 새로 생긴다. **서명 문제와 완전히 별개의 큰 규제 영역**이다.
- 세금계산서·현금영수증·인보이스 증빙은 **전자세금계산서(국세청) 요건**을 별도로 봐야 한다.

### 2-6. 개인정보 리스크 (지금 당장 해당)

- `signature_meta`에 **IP·User-Agent·이메일**, 그리고 **서명 이미지(필적 자체가 개인정보)**를 저장 → **개인정보보호법** 적용.
- 필요: 수집·이용 동의 및 근거, 보관기간, private 버킷/암호화(이미 private + signed URL로 잘 돼 있음), 파기 정책.

## 3. v2 강화 방안 — "더 강화된 느낌"을 주는 법

두 축으로 나눈다. **(A) 실제 법적 신뢰성을 올리는 것**과 **(B) 사용자가 신뢰를 체감하게 하는 것**. 마케팅상 "강화된 느낌"은 B가 크지만, B만 하고 A를 안 하면 과대표시로 오히려 법적 리스크가 커진다. **A를 먼저 깔고 그 위에 B를 얹어야 한다.**

### A. 실제 신뢰성 강화 (우선순위 순)

#### A-1. 신원확인 강화 ★ 최우선
가장 약한 고리. `SignatureProvider` 뒤에 인정 사업자 연동을 추가한다.
- 휴대폰 본인인증(PASS) 또는 카카오·네이버·토스 간편인증 연동
- 서명 직전 1회 인증 → `signature_meta`에 인증 수단·인증 시각·CI/DI 대신 해시화된 인증 참조 저장(원문 식별정보 저장은 지양)
- 인정전자서명 사업자를 쓰면 2-3의 "추정력" 이점에 근접

#### A-2. 제3자 신뢰 타임스탬프(TSA) / 무결성 앵커링 ★
"운영자가 나중에 안 바꿨다"를 외부로 증명.
- `doc_hash`를 공인 TSA(예: 한국정보인증 등) 또는 최소한 외부 불변 저장소에 봉인
- 저비용 대안: 해시를 append-only·write-once 저장(WORM 버킷)하고, 서명 시점 이후 수정 불가하도록 잠금
- 되돌리기(`signed → draft`)로 서명 아티팩트를 지우는 현재 동작은 증거 보존 관점에선 위험 — v2에선 **삭제 대신 무효화 이벤트로 남기고 원본 해시는 보존** 검토

#### A-3. 완결증명서(Audit Trail Certificate) 발급 ★
서명 완료 시 표준 포맷의 증명서 PDF 자동 생성.
- 포함: 문서 해시, 서명자 신원(인증 수단), 서명 시각(TSA 타임스탬프), IP/UA, 동의 이력, 문서 각 페이지 지문
- 계약 PDF에 이 증명서를 첨부 → 분쟁 시 단일 증거물로 제출 가능

#### A-4. 양자 서명(맞서명) 및 서명 요청 링크
현재는 소유자 단독 서명. 실계약은 **상대방도 서명**해야 성립 증거가 완성된다.
- 서명 요청 이메일/링크 → 상대방이 본인인증 후 서명
- 서명 순서·각자 서명 시각·각자 신원을 이벤트 로그에 기록

#### A-5. 서명 시 명시적 동의 캡처
- "본 전자서명을 나의 서명으로 사용하는 데 동의" 체크 → 전자서명법 제3조의 "당사자 합의"를 명문화
- 개인정보 수집·이용 동의도 이 시점에 캡처

### B. 신뢰를 체감하게 하는 UX (A 위에 얹기)

- **서명 완료 배지/타임스탬프**: "2026-07-10 14:32 KST · 문서지문 3f9a…c21 · 휴대폰 인증 완료" 형태로 시각적 확정 표시
- **문서지문(해시) 노출**: 계약 상세·PDF에 축약 해시를 always-on으로 보여 "위변조 감지 가능" 인식을 줌 (이미 PDF엔 있음 → 상세 화면에도)
- **완결증명서 다운로드 버튼**: 사용자가 "증거물"을 손에 쥐는 경험
- **감사 타임라인 뷰**: `contract_events`를 사람이 읽는 타임라인으로 렌더(초안 작성 → 서명 요청 → 상대 서명 → 완료)
- **면책 문구 정확화**: 현재 "법적 효력 없음"을 v2에선 "휴대폰 인증 + 타임스탬프로 무결성·신원을 기록합니다. 공인 전자서명이 요구되는 계약은 별도 확인 필요"처럼 **한 일과 안 한 일을 정확히** 표시 (과대표시 방지)

### 우선순위 로드맵 제안

| 단계 | 항목 | 효과 |
|---|---|---|
| v2.0 | A-1 신원확인(간편인증) + A-5 동의 캡처 + B 배지/해시 노출 | 가장 약한 고리 해소, 체감 신뢰 급상승 |
| v2.1 | A-3 완결증명서 + A-4 맞서명/서명 링크 | 실제 계약 워크플로 완성 |
| v2.2 | A-2 TSA/앵커링 + 증거 보존 정책 정비 | 무결성 최종 방어선 |

## 4. 지금 당장 손볼 것 (v1 범위)

법적 효력을 안 올리더라도, 현재도 정리해두면 좋은 것:
1. **개인정보 처리방침에 서명 데이터(이미지·IP·UA·이메일) 항목 명시** — 수집 근거·보관기간·파기
2. **면책 문구 표현 점검** — "효력 없음"보다 "간이 기록용, 강한 법적 증거가 필요하면 인증 서명 필요"가 더 정확하고 방어적
3. **되돌리기 시 서명 삭제 동작의 문서화** — 사용자가 예상하도록 (WALKTHROUGH엔 있음)
